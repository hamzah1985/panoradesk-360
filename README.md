# PanoraDesk 360

A desktop editor for building interactive 360° virtual tours from panorama photos, and exporting them as self-contained websites that run entirely offline.

Windows desktop app built with Electron, React, and [Photo Sphere Viewer](https://photo-sphere-viewer.js.org/).

> **Status:** first public release. Windows x64 only. The installer is not code-signed yet, so Windows SmartScreen will warn on first run — choose *More info → Run anyway*.

## Features

- Import equirectangular panoramas straight from disk; they're downscaled and thumbnailed automatically
- Place navigation hotspots between scenes, with paired return links kept in sync
- Info markers, per-scene intro text, and a configurable hotspot style system
- Floor plan view with clickable scene pins
- Live preview of the exported tour before you publish
- Export a website-ready folder or ZIP — **no CDN, no internet required at runtime**
- Deploy directly into an existing website folder

Projects are plain folders with a human-readable `project.json` you can edit or
version-control. They live under `Documents/PanoraDesk360/projects/` — unless
Windows has redirected Documents into OneDrive (or another sync client), in
which case the app falls back to `<your-profile>/PanoraDesk360/projects/`.
Tours are large binary data, and cloud sync can evict panoramas to placeholders
that then fail to load offline.

## Install

Download the latest `PanoraDesk 360 Setup <version>.exe` from the [Releases](../../releases) page and run it.

## Build from source

Requires Node.js 20 or newer.

```bash
git clone https://github.com/hamzah1985/panoradesk-360.git
cd panoradesk-360
npm install          # `prepare` builds the viewer bundle automatically
npm run electron:dev # run the app in development
```

To produce the Windows installer:

```bash
npm run electron:build
```

Output lands in `release/`:

- `PanoraDesk 360 Setup <version>.exe` — the installer, roughly 100 MB
- `win-unpacked/` — the unpacked application, roughly 350 MB installed

The build uses the Electron already in `node_modules` (`electronDist` in the
`build` config) rather than re-downloading it. That keeps the packaged runtime
in lockstep with the pinned `electron` devDependency, and avoids a re-download
on every build.

Only `sharp` and `archiver` are runtime dependencies — everything else is
bundled by Vite into `dist/`, so it belongs in `devDependencies` and is
excluded from the installer. Adding a genuinely runtime-required package means
putting it in `dependencies`; putting a build-time package there will bloat the
installer.

### Scripts

| Script | What it does |
|---|---|
| `npm run electron:dev` | Vite dev server + Electron with hot reload |
| `npm run electron:build` | Icons, viewer bundle, renderer build, then the installer |
| `npm run lint` | TypeScript check (`tsc --noEmit`) — must be clean |
| `npm run vendor:bundle` | Rebuilds `electron/vendor/` (Photo Sphere Viewer + the tour player) |
| `npm run icons:generate` | Regenerates app icons from `src/assets/app-logo.svg` |
| `npm run clean` | Removes `dist/` and `release/` |

## How it fits together

```
src/                 React editor UI (renderer)
  export/player.ts   The tour runtime shipped inside every export
  lib/               Shared hotspot rendering, asset resolution, viewer motion
  store/             Zustand state, autosave, undo/redo
electron/
  main.cjs           Main process: project I/O, image processing, export, preview server
  preload.cjs        The entire renderer↔main API surface
  vendor/            Generated — viewer bundle + compiled player
scripts/             Icon generation and the esbuild vendor bundler
```

Two details worth knowing before changing things:

- **`src/export/player.ts` is the single source of truth for exported tours.** It is compiled by `scripts/bundle-vendor.mjs` into `electron/vendor/player.js` and copied into each export as `assets/app.js`. The surrounding HTML and CSS are generated by `generateExportHtml()` / `generateExportStyle()` in `electron/main.cjs`, so element IDs must stay in sync across the two files.
- **Project assets are served over the `app-media://` scheme**, registered in `electron/main.cjs` and produced by `resolveAssetSrc()` in `src/lib/media.ts`. This is deliberate: `file://` subresources are blocked in development, where the renderer is served from `http://localhost:5173`.

## Exported tours

An export is a plain static folder:

```
panoradesk360-<tour-name>/
├── index.html
├── README.md          ← deployment guide written into every export
├── vendor/psv.js      ← viewer + Three.js, bundled locally
└── assets/
    ├── app.js         ← the tour runtime
    ├── tour.json      ← all scene, hotspot, and marker data
    └── panoramas/ thumbnails/ logo/ floorplan/
```

Upload the folder to any static host. Because `fetch()` is blocked on `file://` URLs, opening `index.html` directly from disk will not work — serve it over HTTP (`python -m http.server` is enough for a local check).

## Contributing — take it and run

This started as a personal project and it's open source now because it's more
useful to other people than sitting on a hard drive. Treat it as yours:

- **Fork it, strip it, rebrand it, sell it.** The MIT licence means you don't
  need to ask, and you don't owe anything back.
- **Point AI agents at it.** The codebase is deliberately agent-friendly —
  plain TypeScript and CommonJS, no build magic, no code generation, and the
  architecture notes above exist so a coding agent can orient itself fast. If
  you want to rip out a subsystem or rewrite the exporter with Claude Code,
  Cursor, or anything else, go ahead. That's a legitimate way to use this.
- **Bad code is fine.** Half-working PRs, rough edges, and "I got an agent to
  do this and it seems to work" are all more welcome than nothing.

Two things worth doing before opening a PR: `npm run lint` should pass, and
`npm run electron:build` should still produce an installer. Beyond that, don't
overthink it.

If you build something interesting on top of this, an issue linking to it would
be genuinely nice to see.
